# Shotcaller

Автобатлер в духе доты. Ты тренер: покупаешь героев, расставляешь их по трём линиям, а матч играется сам.
Связки героев работают только внутри одной линии, урон по вышкам и трону копится между раундами.

## Запуск

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # юнит-тесты (Vitest)
npm run typecheck  # vue-tsc
npm run lint       # ESLint, включая правила границ между слоями
npm run balance -- --matches 100   # прогон матчей ИИ против ИИ без браузера
npm run build
```

## Архитектура

Слои зависят только «внутрь». ESLint (`eslint.config.ts`) запрещает обратные импорты.

```
ui ─► application ─► rendering ─► simulation ─► domain ─► content ─► core
```

| Слой | Что внутри | Библиотеки |
|---|---|---|
| `core` | математика, детерминированный RNG, PRD как в доте, фиксированный шаг времени | seedrandom |
| `content` | данные: герои, способности, роли, связки, крипы, правила экономики | — |
| `domain` | матч, игрок, лавка, пул героев, звёзды, доход, ИИ-тренер. Без фреймворков | neverthrow |
| `simulation` | бой на ECS: компоненты, системы, способности, события | miniplex, check2d, mitt |
| `rendering` | отрисовка доски, юнитов и эффектов | PixiJS, gsap |
| `application` | сборка матча, сессия боя, DTO для интерфейса, облачные сохранения | @supabase/supabase-js (загружается, только если облако настроено) |
| `ui` | Vue-компоненты, стор, локализация | Vue, Pinia, vue-i18n, reka-ui, VueUse, vue-draggable-plus |

Главные решения:

- **Симуляция детерминирована и не знает о браузере.** Один и тот же сид даёт один и тот же бой, поэтому её можно тестировать и гонять в node (`scripts/balance.ts`).
- **ECS.** Поведение разложено по системам (`simulation/systems`) и выполняется в фиксированном порядке в `BattleSimulation`. Смерти применяются отложенно в `DeathSystem`, чтобы не ломать итерацию запросов.
- **Шансовые эффекты катятся через PRD** (`core/random/prd.ts`), как в доте: крит Broadsword, баш Giant, уклонение ганкеров. Шанс растёт с каждой неудачей и сбрасывается после срабатывания, поэтому длинных серий везения и невезения не бывает.
- **Способности — стратегии в реестре** (`simulation/abilities/registry.ts`). Новая способность — это новый файл плюс строка в реестре, существующий код не трогаем.
- **Интерфейс читает снимки, а не доменные объекты.** Стор вызывает команды домена (`Result` из neverthrow) и после каждой строит неизменяемый `MatchView`.
- **Рендер подписан на мир ECS и события симуляции.** Логика боя ничего не знает про PixiJS.

## Как добавить героя

1. `content/ids.ts`: добавить id героя и способности.
2. `content/heroes.ts`: английское имя, двухбуквенный значок, роль и характеристики. Имена героев, способностей и предметов не переводятся.
3. `content/abilities.ts`: параметры и английское название способности.
4. `simulation/abilities/<ability>.ts`: реализовать `Ability` и зарегистрировать в `registry.ts`.
5. `ui/i18n/locales/ru.json` и `en.json`: описание способности (числа подставляются из `ABILITY_PARAMS`).
6. `npm run balance` и посмотреть, как новый герой выглядит в статистике.

## Профиль

Профиль тренера хранится локально (`shotcaller/profile` в localStorage) и открывается с плашки в левом верхнем углу стартового экрана или по адресу `#/profile`.

- Правила в `content/profile.ts`: семь рангов по пять звёзд, очки рейтинга за победу и поражение, опыт за матч и кривая уровней.
- Логика в `domain/profile`: `recordMatch` превращает законченный матч в запись истории и обновляет пожизненную статистику, `progression.ts` считает ранг и уровень. Всё это чистые функции с тестами.
- Сохранение в `application/persistence/profileSnapshot.ts` проверяется zod-схемой с версией, как и сохранение матча.
- История хранит последние 20 матчей, а суммарная статистика по героям и связкам копится отдельно и не теряется.

## Облачные сохранения

Необязательны: без переменных окружения игра хранит прогресс только на устройстве и даже не загружает клиент Supabase.

**Как работает.** Игра всегда играет на локальном профиле, облако догоняет его в фоне (`application/cloud`).

- При первом сохранении создаётся гостевой (анонимный) аккаунт. Чтобы продолжить на другом устройстве, игрок привязывает почту (код из письма) или Google и входит там под тем же аккаунтом.
- Законченные матчи и смена имени ставятся в очередь. Каждое сохранение идёт поверх известной ревизии профиля. Если другое устройство успело сохраниться раньше, игра перечитывает облачный профиль и заново применяет свои матчи поверх него (`ProfileSync`), поэтому прогресс с двух устройств складывается, а не затирает друг друга.
- Если прогресс есть и на устройстве, и в аккаунте, в который игрок только что вошёл, игра спрашивает, какой оставить.
- В таблице `profiles` лежит снимок профиля (имя, аватар, статистика), в `matches` — архив всех матчей. Почта хранится только в Supabase Auth.

**Настройка.**

1. Создать проект на [supabase.com](https://supabase.com) (хватит бесплатного тарифа).
2. Применить миграцию `supabase/migrations/20260927120000_cloud_save.sql` (SQL Editor или `supabase db push`). Она создаёт таблицы, правила «видишь и пишешь только свои строки» (RLS), отбирает права у неавторизованной роли и ограничивает размер данных.
3. Authentication → Sign In / Providers: включить **Anonymous sign-ins** и **Email**. Для Google — включить провайдер Google и **Allow manual linking**, иначе гостя нельзя привязать к Google.
4. Authentication → URL Configuration: добавить адрес игры (и `http://localhost:5173` для разработки) в Site URL / Redirect URLs.
5. Authentication → Email Templates: в шаблоны **Magic Link** и **Change Email Address** добавить `{{ .Token }}`, чтобы в письме был код, а не только ссылка.
6. Скопировать `.env.example` в `.env.local` и заполнить. Для деплоя задать те же переменные в настройках хостинга.

```bash
VITE_SUPABASE_URL=https://<project>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...   # или legacy anon key
VITE_SUPABASE_GOOGLE=true                          # если настроен Google
```

**Безопасность.** В клиент попадает только публичный ключ: доступ к данным ограничивает RLS. Секретный (`sb_secret_…`) или `service_role` ключ игра распознаёт и отказывается с ним работать. Стоит включить CAPTCHA для анонимных входов и время от времени удалять старых гостей без привязки (Supabase описывает это в разделе про anonymous sign-ins).

**Общий рейтинг позже.** Рейтинг в `profiles` считает клиент, поэтому для общей таблицы лидеров ему верить нельзя. Бой детерминирован (сид + составы), так что сервер (Supabase Edge Function на TypeScript) сможет пересчитать матч тем же кодом симуляции и начислить рейтинг сам. Пока общего рейтинга нет, накрутка вредит только самому читеру.

## Как выпустить патч

1. Поднять версию: `npm version <x.y.0> --no-git-tag-version` для релиза или `<x.y.z>` для исправлений поверх него.
2. Добавить патч в начало `PATCH_NOTES` в `ui/patchNotes/notes.ts` с версией `x.y` или `x.y.z`: дата, заголовок, короткое описание и изменения по разделам (общие, предметы, роли, герои, интерфейс, исправления). Каждая строка пишется на русском и английском, значения выделяются `**так**`.
3. `npm test` проверит порядок версий, совпадение с `package.json` и то, что у каждой строки есть оба перевода.

Страница патчноутов открывается с карточки на стартовом экране и живёт в адресе `#/patches/<версия>`, так что на патч можно дать ссылку. Карточка показывает бейдж «Новое», пока игрок не открыл последний патч.
